# One-Shot 프로토콜 ($one-shot)

`$one-shot`은 **이미 확정된 작은 작업 단위**를 `$kickoff`부터 PR 리뷰 수렴까지 **사용자
개입 없이 한 흐름으로** 밀어붙이는 무인 오케스트레이션 절차다. 단계마다 승인 프롬프트를
띄우지 않고, 대신 **`$one-shot` 호출 자체를 사용자의 명시적 포괄 사전위임으로 간주해** 각
승인 게이트를 자동으로 통과·기록한다.

이 프로토콜은 각 단계를 **재정의하지 않는다.** kickoff·prd-helper·adr-helper·
feature-develop·make-pr의 절차는 각자의 정본을 그대로 따르고, `$one-shot`은 그 위의
**오케스트레이션 규율**(무인 진행, 승인 자동 부여, 종착점, 정지 조건)만 정의한다.

## 언제 쓰는가 (그리고 언제 쓰지 않는가)

- **쓴다:** 무엇을 만들지 이미 정해졌고, 하나하나 확인받지 않아도 될 만큼 **작고 명확한**
  작업 단위. 사용자가 "이거 알아서 PR까지 해줘" 식으로 전 과정을 위임한 경우.
- **쓰지 않는다:** 무엇을 할지 아직 안 정해진 열린 아이디어(→ 먼저 `$next-feature`). 제품
  방향이 갈리거나 되돌리기 어려운 결정이 얽힌 큰 작업. 그런 작업은 단계마다 사용자 판단이
  필요하므로 일반 흐름(`$kickoff` → `$prd-helper` → …)을 개별로 태운다.

`$one-shot`은 `$next-feature`를 대체하지 않는다. "무엇을 만들지"는 사용자가 준다(작업 단위,
작업 설명, 또는 GitHub 이슈 번호). 진행 중 큰 제품 결정이 튀어나오면 그건 애초에 one-shot
대상이 아니었다는 신호다 — 무인 진행을 멈추고 사용자에게 돌린다(아래 "정지 조건").

## 입력과 출력

```txt
입력: 확정된 작업 단위(또는 명확한 작업 설명 / GitHub 이슈 번호) + 사용자의 포괄 위임 지시
출력: 브랜치+raw 골격 → (feature면) PRD/ADR 사전승인·구현·최종확정 → 커밋 → PR 생성
      → (스킬 있으면) PR 리뷰 수렴 clean → 여기서 정지(머지·정리는 사용자 확인 후 수동)
```

## 포괄 위임과 승인 자동 부여 (핵심 계약)

승인은 이 하네스의 심장이다. `$one-shot`은 그 게이트를 **없애지 않고**, 사람 대신 **포괄
위임을 근거로 자동 통과**시킨다. 정직성은 두 가지로 지킨다.

1. **quote는 실재하는 위임 발화다(합성 금지).** 각 게이트의 `harness:approve --quote`에는
   사용자가 `$one-shot`을 호출하며 남긴 **실제 위임 지시를 verbatim으로** 넣는다. 발화를
   지어내지 않는다 — 위임 발화는 실제로 존재한다. (의도·아이디어 발화가 아니라 "PR까지
   알아서 진행하라"는 명시적 위임이어야 한다. 그런 발화가 없으면 `$one-shot`을 돌리지
   않는다.)
2. **transport는 `one-shot`으로 찍어 자동 부여임을 드러낸다.** `harness:approve
   --transport one-shot`으로 기록하면, `state.md` 승인 이벤트의 transport 컬럼에 `one-shot`이
   남는다. 이는 감사자에게 **"이 승인은 사람이 게이트마다 개별 승인한 게 아니라 one-shot
   포괄 위임으로 자동 부여됐다"**를 명시한다. 개별 승인인 척 위장하지 않는다.

즉 각 승인 게이트는 아래 형태로만 전환한다(에이전트가 frontmatter status를 직접 고치지
않는 규율은 그대로 — 런타임 훅과 `harness:check`가 막는다).

```sh
# 사전 승인 (feature 진입 게이트)
npm run harness:approve -- --unit docs/raw/feature/<slug> --quote "<사용자의 포괄 위임 발화 verbatim>" --transport one-shot [--adr]
# 최종 확정 (PR 직전)
npm run harness:approve -- --unit docs/raw/feature/<slug> --quote "<사용자의 포괄 위임 발화 verbatim>" --transport one-shot --final [--adr]
```

## Phase 0: 진입과 분류

1. 입력이 **확정된 작업 단위**인지 확인한다. 열린 아이디어("뭐 하지?")면 `$one-shot`을
   멈추고 `$next-feature`로 안내한다 — one-shot은 후보 발굴을 하지 않는다.
2. 사용자의 **포괄 위임 발화**를 캡처한다(각 게이트 quote로 재사용). 위임이 아니라 단순
   의도·설명이면 무인 진행 근거가 없으므로 일반 흐름으로 돌린다.
3. 유형(feature/bugfix/chore)을 "결정의 성질"로 판정한다(`kickoff.md`의 유형 정책과 동일).
   GitHub 이슈 번호로 시작하면 이슈를 읽고 판정한다(`kickoff.md` "GitHub 이슈로 시작").
4. **스코프 통보(승인 프롬프트 아님).** "이 작업을 PR 리뷰 수렴까지 무인 진행합니다"를 한
   줄로 알리고 시작한다. 위임 범위를 고정해 이후 단계에서 되묻지 않기 위함이다.

## Phase 1: Kickoff

`$kickoff` 정본을 따른다 — 브랜치와 raw path를 1:1로 맞추고 골격을 만든다. 브랜치 상황감지
규율(`kickoff.md` "브랜치 처리")도 그대로다. 단 **`main`/master + clean이 아니어서 kickoff이
자동 전환하지 않는 경우**(다른 브랜치, 무관한 WIP, detached HEAD 등)는 워크트리 격리 vs
현재 위치 checkout이 사용자 판단이므로 — 무인으로 임의 결정하지 않고 **정지해 사용자에게
묻는다**(이것도 아래 "정지 조건"). clean한 정상 경로면 그대로 자동 진행한다.

## Phase 2: PRD/ADR (feature 단위만)

`$prd-helper` 정본으로 PRD를 `review`까지 작성하고, `## ADR 필요 여부`를 판정한다. 그다음
사전 승인을 **자동 부여**한다(위 "승인 자동 부여").

- **ADR 불필요:** `$prd-helper`의 "PRD 단독 사전 승인" 지점에서 사용자에게 묻는 대신,
  포괄 위임 quote + `--transport one-shot`으로 PRD를 `pre-approved`로 전환한다.
- **ADR 필요:** `$adr-helper` 정본으로 ADR을 `proposed`까지 작성한 뒤, PRD·ADR **통합 사전
  승인**을 `--adr --transport one-shot`으로 자동 부여한다.

bugfix/chore는 PRD/ADR 승인축이 없다. 이 Phase를 건너뛴다(bugfix는 `bugfix.md`, chore는
notes-only).

## Phase 3: 구현

`$feature-develop` 정본을 따른다. 자율 fan-out 구간(구현·테스트·검증)은 그대로 병렬로
돌린다 — 원래 이 구간은 사용자에게 묻지 않는 자율 구간이라 one-shot과 정합적이다. 빌드 중
PRD/ADR을 개정해야 하면(`feature-develop.md` Phase 0.6): 포괄 위임 범위 안의 사소한 본문
정리는 진행하되 `state.md` 단계 로그에 남기고, **요구·결정 자체가 바뀌는 개정은 제품 판단**
이므로 정지해 사용자에게 확인받는다.

## Phase 4: Make PR

`$make-pr` 정본을 따른다. 최종 확정을 **자동 부여**한다: 포괄 위임 quote + `--transport
one-shot --final`(+ ADR 있으면 `--adr`)로 `approved`/`accepted`로 전환한 뒤,
`harness:gate`를 신선하게 판정하고 `commit-protocol`로 확정 커밋을 만들고 push·PR을
생성한다. bugfix/chore는 승인 플립을 건너뛰고 곧바로 게이트·커밋·PR로 간다.

## Phase 5: PR 리뷰 수렴 (스킬이 있을 때만)

**PR에 달린 리뷰를 수렴·반영하는 스킬이 현재 런타임에 설치돼 있으면**, 그 스킬을 호출해 리뷰
지적을 검증·반영·재요청하며 clean 판정까지 밀어붙인다. 이런 스킬은 이 하네스가 배포하지
않는 **선택적 외부 가속기**다(`$deep-interview` 관용구와 동일 — `AGENTS.md` "Skill
Invocation Markers"). **설치돼 있지 않으면 이 Phase를 건너뛰고** PR만 생성한 채 그 사실을
보고한다. 부재를 이유로 실패로 처리하지 않는다.

리뷰 수렴 중에도 승인 게이트 규율은 유지된다: 리뷰 반영이 PRD/ADR 결정을 뒤집는 수준이면
그건 제품 판단이므로 정지해 사용자에게 돌린다.

## 종착점: 리뷰 clean에서 정지 (머지는 수동)

PR 리뷰가 clean이고 `harness:gate`가 green이면 **여기서 정지하고 결과를 보고한다.** 머지와
브랜치·워크트리 정리는 **되돌리기 어려운 outer-facing 작업**이라 무인 파이프라인의 범위
밖이다.

- **머지·정리를 담당하는 스킬이 설치돼 있으면**, 실행하지 않고 "다음 단계로 이 스킬을
  쓰면 된다"고 **안내만** 한다(역시 선택적 외부 가속기다 — 이름을 하드코딩하지 않고 역할로
  가리킨다). 실제 머지·정리는 사용자가 확인 후 명령한다.
- 스킬이 없으면 PR 링크와 상태만 보고한다.

## 정지 조건 (무인이라고 삼키지 않는다)

아래 중 하나라도 만나면 무인 진행을 **멈추고 사용자에게 보고·확인**한다. 무인 진행은
"실패를 조용히 넘기는 것"이 아니다.

- 어느 단계든 게이트가 red거나(`harness:check`/`harness:gate` 실패), 구현이 막히거나, 리뷰
  반영에 실패한다.
- 제품 방향이 실제로 갈리는 결정, 사용자가 골라야 할 트레이드오프, PRD/ADR 요구·결정을
  뒤집는 개정이 필요해진다(one-shot 대상이 아니었다는 신호).
- kickoff이 브랜치를 자동 전환할 수 없는 상황(워크트리 격리 vs checkout 선택)이다.
- 위임 발화가 실제 위임이 아니라 의도·아이디어에 그친다(애초에 진입하지 않는다).
- 머지처럼 되돌리기 어려운 단계에 도달한다(종착점).

## 실패 모드

- **나쁨:** 승인 게이트에서 사용자가 하지도 않은 개별 승인 발화를 지어내 quote로 넣는다.
- **좋음:** 실재하는 포괄 위임 발화를 verbatim으로 넣고 `--transport one-shot`으로 자동
  부여임을 감사 컬럼에 드러낸다.

- **나쁨:** 게이트가 red인데 무인이라는 이유로 넘기고 커밋·PR까지 밀어붙인다.
- **좋음:** 게이트 실패에서 정지하고 원인과 함께 사용자에게 보고한다.

- **나쁨:** 열린 아이디어를 받고 one-shot이 후보까지 지어내 바로 구현한다.
- **좋음:** 확정된 작업 단위만 받고, 열린 요청이면 `$next-feature`로 돌린다.

- **나쁨:** 리뷰 clean 후 무인으로 머지·정리까지 해버린다.
- **좋음:** 리뷰 clean에서 정지하고, 머지·정리 스킬이 있으면 안내만 한 뒤 사용자 확인을 받는다.

- **나쁨:** 빌드 중 요구·결정을 뒤집는 개정을 무인으로 반영한다.
- **좋음:** 요구·결정 변경은 제품 판단이므로 정지해 확인받고, 사소한 본문 정리만 진행하며 단계 로그에 남긴다.
