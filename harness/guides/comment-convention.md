# 코드 주석 컨벤션 (Comment Convention) — 정본의 복사본을 코드에 두지 않는다

이 가이드는 구현 시 코드·테스트에 **어떤 주석을 남기고 어떤 주석을 지울지**의 보편 규칙이다.
`$feature-develop`의 구현(Phase 2)·자체 코드리뷰(Phase 3.7)와 `guides/code-review-guideline.md`의
리뷰 렌즈가 이 규칙을 대조한다. 프로젝트마다 다른 축(이슈 표기법·정본 경로 체계·베이스 스타일
가이드)은 **이 하네스가 규정하지 않고 레포 관례에 위임**한다(맨 아래 "레포에 위임하는 축").

## 로딩 규칙 (토큰)

전체를 항상 로드하지 않는다. 아래 "관문"과 "허용목록"이 코어이며, 구현·리뷰가 주석을 판정할 때
그 두 절만 대조하면 된다. 나머지(형식·`@see`·롤아웃)는 필요할 때 펼친다.

## 핵심 — 주석의 수신자는 다음 독자다

리뷰어에게 하는 말은 PR이 머지되는 순간 노이즈가 된다. WHY(인과 서사·실측 수치·기각 이력·
결정 ID)는 정본의 소유물이다 — 결정 근거는 **PRD/ADR**(그런 체계가 있는 레포) 또는 **이슈·설계
문서**가, 변경 배경은 **커밋·PR**이 가진다. **코드에 옮겨 적지 않는다.** 정본이 갱신돼도 코드 안
복사본은 따라오지 않아 조용히 거짓이 된다. 형식은 프로젝트의 베이스 스타일 가이드를 따르고, 이
가이드가 더하는 것은 **양·소유권 축**이다.

## 관문 — 문장마다 건다. 걸린 문장은 지우고, 남는 문장이 있으면 그것만 남긴다

1. **정본에 있는가?** 정본(PRD/ADR·이슈·커밋·PR)에 있거나 거기 있어야 할 문장이면 지운다 —
   결정 ID 재서술, 작업 배분(태스크 번호·산출물 순번), 실측 수치와 날짜, 기각 이력, 변경 이력
   (「기존에는 ~였다」·「리뷰가 찾아냈다」). **단 제약 자체는 남는다** — 이 관문이 막는 것은
   서사·수치·이력·ID지 제약이 아니다.
2. **이름이 이미 말하는가?** 심볼명·타입·`describe`/`it` 제목으로 알 수 있으면 지운다 — 파일명
   재진술, 같은 계약을 선언마다 되풀이하는 것. 애매하면 주석 대신 **이름을 고치거나 작은 함수로
   추출**한다.
3. **불변식인가?** 깨지면 버그가 되는 주장은 **테스트가 봉인한다.** 봉인이 없으면 테스트를 먼저
   쓰고, 봉인이 있으면 그 사실을 주석에 적지 않는다 — 다만 **허용목록에 걸리는 문장은 봉인과
   무관하게 1줄까지 남는다.** 「테스트가 잡지 못한다」고 적는 것은 주석이 필요하다는 신호가 아니라
   **테스트가 빠졌다는 신호**다.
4. 남은 문장은 허용목록에서 **항목 하나를 지목**한다. 못 하면 지운다.
5. **5줄을 넘기면 그건 주석이 아니라 결정 문서다** — `/**`·`*/`·빈 줄을 뺀 **내용 줄**로 센다.
   **`@example`은 코드 샘플이라 세지 않는다**(그 태그부터 다음 블록 태그 직전까지). 허용목록 ④도
   예외다. 린트로 이 상한을 걸 수 있으면 JSDoc과 `//` 연속 묶음 양쪽에 건다(선택 — 없어도 관문으로
   판정).

## 허용목록 — 여기 없으면 쓰지 않는다

① **코드가 보여줄 수 없는 외부 제약** — 라이브러리·브라우저·런타임·서버 API의 실제 동작
② **값의 단위·경계·falsy 의미**
③ **순서 의존·invariant** — 이 호출이 저것보다 앞/뒤여야 하는 이유
④ **공개 API의 문서 주석** — **다른 모듈·패키지가 import하는 심볼**의 계약. 딥 임포트되는 심볼도
   공개로 본다. **여기만 줄 수 상한이 없다**
⑤ **테스트 파일 최상단 봉인 선언 1줄** — `describe` 제목이 말하지 않는 축이 있을 때만
⑥ **중요한 이슈 표시** — 한 줄 summary + `@see` 하나(아래)

**이 가이드는 테스트 파일 주석에도 그대로 적용된다.** 코드에서 밀어낸 WHY가 테스트 주석으로
이주하면 총량은 그대로다 — 봉인 근거는 `it` 제목과 단언이 말한다.

## 형식

- `/** */` = 문서 / `//` = 구현 주석. **여러 줄 구현 주석은 `//`를 반복**한다(`/* */` 금지).
  별표 박스·꼬리 주석(`const x = 1; // 설명`) 금지
- **파일 줄 번호를 적지 않는다** — 패치 하나에 조용히 거짓이 된다. **심볼명으로 쓴다.** 라이브러리
  내부라 지목할 심볼이 없으면 `패키지명 버전 함수명`(`@some/lib 3.2 createThing`)
- 타입 재선언(`@param {string}`·`@implements`·`@override`) 금지 — 타입 시스템이 읽지 않는다.
  `@param`/`@returns`는 **정보를 더할 때만**
- `TODO`/`FIXME`는 부득이할 때만 쓰고 **이슈 참조를 반드시 동반**한다(레포의 이슈 표기법)
- **마크다운을 쓰지 않는다** — 헤딩·볼드·이탤릭·리스트·표·인용·링크·이모지·경고 기호. **예외는
  `@example`의 코드 펜스뿐.** 식별자·리터럴을 감싸는 백틱은 꾸밈이 아니라 **구분**이라 허용한다
  (정규식·CSS 값·심볼명). 주석에 헤딩과 불릿이 필요해졌다면 그건 주석이 아니라 문서다

## 중요한 이슈는 한 줄 summary + `@see` 하나

**「중요한」의 기준** — 모르고 고치면 정본의 결정이 뒤집히거나 외부 계약이 깨지는 경우. **어떤
업무에서 만들어졌다는 사실 자체는 중요함이 아니다**(이력 추적 소관). summary는 **제약**을 말하고
근거는 링크 너머에 둔다 — 결정 ID·실측 수치를 요약에 넣지 않는다. `@see`는 `/** */`에만 쓰고
**하나만** 건다 — 여러 이슈에 걸치면 가장 최근 것, 같은 이슈의 결정 문서가 PRD와 ADR 둘 다면 ADR.
괄호로 결정 ID를 덧붙이지 않는다.

**대상 선택**: 정본이 *그때 왜 그렇게 정했나*이면 이슈·결정 문서를(결정 문서 체계가 있으면 그
경로, 아니면 이슈 참조), *지금 무엇이 맞나*인 제품 스펙이면 스펙/위키를 가리킨다. **표기 형식은
레포 관례를 따른다**(아래 위임 축).

```ts
// 나쁜 예 — 결정 ID 재서술 · 근거 서사 · @see 2개에 괄호 주석. 내용 여러 줄
/**
 * 입력의 heading 요소를 보존만 하는 노드.
 * FR8·FR9 / ADR D1 — 생성/보존 분리 근거 · levels 파생 구조 여러 줄 …
 * @see <결정문서 A> (D1 생성/보존 분리 · D2 숨은 진입 경로)
 * @see <결정문서 B> (D4 부모 키맵 omit · D5 levels 보존)
 */

// 좋은 예 — 내용 2줄
/**
 * heading 보존 전용 — 생성 경로는 닫혀 있고, levels를 줄이면 유입 제목이 파싱되지 않는다.
 * @see <결정문서 하나>
 */
```

**예시와 조항이 어긋나면 조항이 이긴다** — 예시가 갱신 대상이다.

## 기존 주석을 고칠 때 (롤아웃 완료까지 한시)

1. **관문을 문장마다 건다.** 허용목록에 남는 문장이 하나라도 있으면 삭제가 아니라 **그 문장만
   남긴다.** 판정·수정 단위는 줄 범위가 아니라 **주석 블록 전체**다 — 범위를 잘라 지우면 문법이
   깨진다.
2. 지우는 문장이 **불변식**이면 봉인처(테스트)를 지목하고, **지목한 단언을 지우거나 뒤집어 그
   테스트가 실제로 실패하는지 확인**한다. 통과하면 비판별 테스트라 봉인이 아니다. 「전체 테스트
   통과」는 근거가 아니다 — 코드를 지워도 전량 통과하는 경우가 있다.
3. 정본에 같은 내용이 있으면 **이관이 아니라 삭제**이며 2의 봉인 요구가 면제된다. **없으면 정본에
   먼저 적고 지운다.** 주석 정리 커밋은 기능 커밋과 분리한다.

**밀도 목표치(%)를 세우지 않는다** — 밀도 목표는 가짜 주석을 유도한다. 판정은 **`@see` 밖의**
결정 ID·이슈번호 인용 수, 5줄 초과 블록 수, 신규 봉인 테스트 수로 한다.

## 레포에 위임하는 축 (이 하네스가 규정하지 않는다)

아래는 프로젝트마다 다르다. **레포의 기존 규칙을 따르고, 규칙이 없으면 가장 널리 쓰이는 관례를
폴백**으로 쓴다:

- **이슈·정본 참조 표기법** — `@see`/`TODO`가 가리키는 대상의 형식. 이슈 트래커가 있으면 그
  이슈 참조 표기(커밋 제목과 같은 표기라 `log --grep`으로 찾히는 형태), 결정 문서 체계
  (`docs/…/adr.md` 등)가 있으면 그 경로, 제품 스펙이면 스펙/위키 링크. 레포에 확립된 관례가 없으면
  그 생태계에서 가장 흔한 이슈 참조 형식을 쓴다.
- **베이스 스타일 가이드** — 형식(따옴표·`@param` 서술 등)의 정본. 프로젝트에 정해진 게 있으면
  그것, 없으면 언어별 가장 널리 쓰이는 것(예: TS/JS는 Google TypeScript Style Guide)을 폴백한다.
- **5줄 상한의 린트 강제** — 걸 수 있으면 걸고(선택), 없으면 관문 5로 판정한다.
